# ETL cleaning and design decisions

Every anomaly found by `etl/profile_raw.py` (output in `out/profile_report.json`) is listed here, with how it was handled. The `[D#]` tags are referenced in `sql/transform_load.sql`.

| # | Finding (from profiling) | Decision | Why |
|---|---|---|---|
| D1 | The official download URL returned 404/redirect during the build window. The data came from a public GitHub mirror. That mirror split `studentVle` into 8 files and re-saved them with a pandas index column. | Concatenated the 8 parts and dropped the index column. Row counts match the dataset paper (10,655,280 / 32,593 / 173,912 …). As a second check, the clickstream was compared with an independent Hugging Face mirror: same row count, but that copy caps `sum_click` at 6 (max 6 vs 6,977), so it is a cleaned derivative and was not used. | Provenance: reconciliation starts from a file whose counts match the source publication. |
| D2 | 11 `assessments` rows (all type *Exam*) have no `date`. | `due_day` = last day of the presentation; `due_day_imputed = 1`. | The OULAD documentation states that a final exam with a missing date falls at the end of the presentation. The flag keeps the imputation visible. |
| D3 | `imd_band` is NULL for 1,111 enrollments. The value `10-20` is missing its `%` (3,516 rows). | NULL becomes `'Unknown'`, and `'10-20'` becomes `'10-20%'`. | Without the fix, a GROUP BY splits the band in two. `Unknown` keeps these rows in the audit as an explicit group. |
| D4 | `age_band` differs across enrollments for 72 students. The other demographics never vary. | `age_band` sits on `dim_enrollment` (its value at that presentation). The stable attributes sit on `dim_student` (Type 1). | This puts each attribute at the grain where it is actually constant. A Type-2 student dimension would have been overkill for 72 rows. |
| D5 | `date_registration` is NULL for 45 enrollments. | Kept NULL in the warehouse. The feature mart imputes the median and adds a `reg_date_missing` flag. | The warehouse stores what was observed, and the mart makes the modelling choice. |
| D6 | Clickstream days run from −25 to 269. Submission days also go negative (banked work). | `week_num = FLOOR(day/7)+1`, so week 1 = days 0–6 and weeks ≤ 0 are pre-start. `dim_course_week` covers every week seen in either source. | Relative course week makes presentations of different lengths and start dates comparable, which a calendar date would not. |
| D7 | 20 activity types. | `dim_activity` with a 4-group hierarchy (content / navigation / communication / assessment), plus member 0 `(no activity)`. | Activity type is a dimension, not 20 pivoted measure columns, so new types need no schema change. |
| D8 | 2,195,960 clickstream rows repeat a (student, site, day) natural key. | **Summed, not dropped.** | These are separate interaction records for the same day, not duplicates. Dropping them would lose 20% of rows and break the click-total reconciliation. |
| D9 | 3,365 enrollments have no VLE rows at all. Students who clicked nothing in a week otherwise leave no trace. | One `(no activity)` fact row for every enrollment-week inside the **registered span** (registration week, or week 1 if later, through the unregistration week or the end of the presentation). | "Clicked nothing in week 3" becomes a row that can be counted. No rows are made after a student has left, so withdrawals are not inflated with fake inactivity. |
| D10 | 1,909 submissions are `is_banked` (carried over from a previous presentation). | Kept, with the flag. | They are real results. Analysts can filter them out. |
| D11 | 173 submissions have no `score`. | Kept with a NULL score and NULL weighted_score. | The submission happened. Imputing a score would invent data. |
| D12 | 93 *Withdrawn* enrollments have no unregistration date. 9 enrollments have an unregistration date but are not *Withdrawn*. | Label taken from `final_result` (the outcome of record). Registered span uses the date when present. | `final_result` is the ground truth the project predicts. |
| D13 | 5,040 enrollments unregistered before day 28. 3,097 of them did so on or before day 0. | **Excluded from the modelling population** (kept in the warehouse). | By the week-4 alert these students have already left, so an alert cannot help them, and keeping them would inflate accuracy with trivially predictable cases. |
| D14 | Found by OLAP query Q09, not by the profiler: in BBB, CCC and DDD, 97–100% of **CMA** submissions arrive 2–3 days after the listed `date`. In FFF and GGG, every CMA shares one end-of-module date. | `is_late` is kept as defined (`date_submitted > due_day`), but lateness is interpreted **for TMAs only**. The CMA `date` is not a deadline in the same sense across modules. | A metric that is 100% for whole modules is a semantics problem, not a behaviour. The report flags it rather than re-defining the source's dates. |
